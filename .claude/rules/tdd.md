# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 1. 적용 기준

### 반드시 적용

- **비즈니스 로직**
- **API** (엔드포인트, 요청/응답 처리, 에러 매핑)
- **유틸 함수**
- **버그 수정** (재현 테스트를 먼저 작성하고 실패를 확인한 뒤 수정한다)

### 불필요

- **타입 정의**
- **설정 파일**
- **순수 UI** (로직 없는 마크업/스타일)
- **SQL**

경계가 모호하면 **적용 대상으로 간주한다.**

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 잘못된 셋업으로 인한 실패는 RED로 인정하지 않고 테스트를 고친다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 분기, 확장 포인트를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해 통과를 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 수정 후마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED부터 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 **프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작한다.**

- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다.
- 삭제 후에는 테스트를 먼저 작성하고, 코드는 처음부터 다시 쓴다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순한 코드가 가장 자주 회귀한다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 구현에 맞춰 작성되어 결함을 잡지 못한다. 그리고 나중은 오지 않는다. |
| 시간이 없다 | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. TDD가 더 빠르다. |
| 삭제하면 낭비 | 이미 쓴 코드는 매몰 비용이다. 검증되지 않은 코드를 유지하는 것이 더 큰 비용이다. |
| 프로토타입이다 | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 테스트 없이 쓰고 반드시 버려라. 유지할 코드라면 TDD를 따른다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 **`CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 그것을 우선한다.**
- **이 파일은 기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
