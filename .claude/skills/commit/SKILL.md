# commit

변경사항을 분석하여 컨벤션에 맞게 커밋하는 스킬.

## 절차

### 1. 변경사항 분석

다음을 병렬로 실행한다.

- `git status` — 변경/추적되지 않는 파일 확인
- `git diff` (unstaged) 와 `git diff --staged` (staged) — 실제 변경 내용 확인
- `git log --oneline -10` — 기존 커밋 스타일 참고 (커밋 이력이 없으면 생략)

주의:
- `.env`, 키/토큰, 인증 정보, 대용량 바이너리, `node_modules/`, 빌드 산출물이 변경에 포함되어 있으면 커밋 대상에서 제외하고 사용자에게 알린다.
- untracked 파일은 내용을 읽어 커밋 대상인지 판단한다.
- 변경사항이 없으면 그 사실만 알리고 종료한다.

### 2. 논리적 단위로 분류

- 변경을 **목적 기준**으로 묶는다 (파일 단위가 아니라 "무엇을 위한 변경인가" 기준).
- 서로 다른 목적(기능 추가 + 버그 수정 + 설정 변경 등)이 섞여 있으면 **여러 커밋으로 분리**한다.
- 한 파일 안에 여러 목적이 섞여 있으면 `git add -p` 대신 사용자에게 분리 여부를 묻는다 (대화형 플래그는 사용 불가).
- 각 커밋에 포함할 파일 목록을 정리한다.

### 3. 한국어 커밋 메시지 작성

형식:

```
<타입>: <요약>

<본문 (선택)>
```

타입:
| 타입 | 용도 |
|------|------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `chore` | 빌드·설정·의존성·문서 등 기타 작업 |

규칙:
- 요약은 한국어, 50자 내외, 마침표 없이 작성한다. (예: `feat: 컴포넌트 생성 API 엔드포인트 추가`)
- "무엇을"보다 **"왜/무엇이 달라졌는지"** 가 드러나게 쓴다.
- 본문은 요약만으로 부족할 때만 작성한다 (변경 이유, 주요 영향).
- 기존 커밋 이력에 스타일이 있으면 그에 맞춘다.

### 4. 바로 커밋

1. 승인을 기다리지 않고 분류한 커밋 단위대로 바로 커밋한다. 단, 다음 경우에만 멈추고 사용자에게 묻는다:
   - 민감 파일(`.env`, 키/토큰 등)이 섞여 있어 제외 여부가 불분명할 때
   - 한 파일 안에 여러 목적이 섞여 분리 여부 판단이 필요할 때
2. 커밋 단위마다:
   - 해당 파일만 이름을 지정해 `git add <파일...>` (`git add -A` / `git add .` 금지)
   - `git commit` 실행 (메시지는 heredoc 으로 전달)
   - 시스템 컨텍스트에 커밋 attribution 지침이 있으면 메시지 끝에 따른다.
3. 모두 끝나면 `git log --oneline` 과 `git status` 로 결과를 확인해 요약 보고한다.

## 금지 사항

- `git push`, `--amend`, `--no-verify`, `reset --hard` 등 요청받지 않은 위험/외부 영향 작업
- pre-commit hook 실패 시 우회 — 원인을 고쳐서 **새 커밋**으로 다시 시도한다.
